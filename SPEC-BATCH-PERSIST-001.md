# SPEC-BATCH-PERSIST-001 — Persistent batch execution records (C-01)

- **Version**: v2.8 FROZEN (2026-11-12, Decision 103)
- **Status**: FROZEN — Decision 103 (2026-11-12, System Development Lead decision). Kohaku Tier 1 ADOPT (CONS-20261112-145, P0=0/P1=0/P2=1); Mitsuki final review ADOPTABLE 9.7/10 (P0=0/P1=0/P2=0).
- **Parent**: v2.7 DRAFT (Kohaku CONS-20261112-145 ADOPT). This v2.8 applies only CONS-145's P2-01 (§5: the real-device power-loss-equivalent test is mandatory for releasing the phone-side durability gate), using Kohaku's exact wording. No other change from v2.7.
- **Addresses**: CONS-131 condition C-01 (A1: /batch exactly-once vs retry).
- **Related**: Decision 49 (A-4 batch idempotency, memory-only), Decision 73 (P0-03, count cap removed), Decision 102 (C-03 correction record).
- **Scope**: Android app only (`HttpBridgeServer.java`, `BridgeAccessibilityService.java`, new `BatchRegistry`). VM-side Python client: only the UNKNOWN handling (no re-send, report for manual confirmation), the new 503 (`persist_failed` / `batch_store_unavailable` / `batch_store_full` / `batch_store_durability_unverified`) handling, and the permanent batch_id reuse ban (§2.10). No protocol version change (stays v1).

## 1. Problem

Decision 49 states batch idempotency is "Memory only: no exactly-once across a process restart (a stated design constraint)". The client retry policy re-sends the same batch_id on transient failures. Across a restart, the re-sent batch_id re-executes as a new batch. A re-executed batch can double-send, double-confirm, double-insert text, or repeat a settings change. If the batch touches an external service, that can mean financial loss or an unintended transaction (CONS-131 A1, P1).

This SPEC adopts **at-most-once** for the phone side: the Bridge never executes the same batch_id twice. Strictly exactly-once with an external app cannot be guaranteed without a transaction with that system; the Bridge guarantees only that it does not re-execute the same ID. When the outcome is unknown, the VM must confirm manually (see §2.6).

The governing principle is: **never let an operation whose outcome is unknown proceed to an easy re-execution.** The design aims to prevent re-execution, not to maximize batch success.

## 2. Design

### 2.1 BatchRegistry — the sole authority (C8)

All batch identity, state, and persistence are managed by one component, `BatchRegistry`. It is the **sole authority** for batch records. There is no dual management with the old in-memory cache.

- `BridgeAccessibilityService` no longer owns batch identity or the `batchCache`. It executes only batches the Registry permits, and reports results back to the Registry. It never registers an ID, never decides replay vs new, and never stores a result on its own.
- `HttpBridgeServer` never touches batch state directly. It calls the Registry for the admission decision and the service for execution, in the order fixed in §2.3.
- The Registry owns: the in-memory record map, the persistent file, the single lock (§2.3), the startup state (§2.5), and the capacity policy (§2.7).
- Rationale: if the Registry and the old cache both tracked IDs, they could disagree (Registry says UNKNOWN while the cache says running; Registry says FAILED while the cache has no entry; after a restart the cache is empty so a re-sent ID looks new). One authority removes that whole class of contradiction.

The Registry is implemented together with the Executor (Stage 2 executor-first in SPEC-KOTLIN-MIGRATION-001 v2.2). The execution responsibilities are organized before the migration; the Registry is not separated from the Executor.

### 2.2 Persistent record and format (C7)

Each batch is recorded in a persistent JSON file, `batch_records.json`, in the app's private files directory.

**File format (v1 of the format):**
- Top level: `{"format_version": 1, "records": [...], "recoveryPending": false, "recoveryInfo": null}`. `recoveryPending` is true only while the store is in the recovery-verification state after a backup restore (§2.5). `recoveryInfo` is null when no restore has happened, and otherwise an object describing the last restore (`restoredAt`, `backupUsed`, `note`, plus `completedAt` / `completedBy` once the operator completes verification). Both fields are persisted in the same atomic write as the records, so the recovery gate survives a restart.
- One record per batch_id: `batch_id` (string, max 128 chars), `payload_hash` (string, hex SHA-256, 64 chars), `status` (one of `IN_PROGRESS`, `COMPLETED`, `PARTIAL`, `FAILED`, `UNKNOWN`), `result` (the full BatchResult JSON, or null while in progress), `createdAt` (epoch ms), `expiresAt` (epoch ms), `tombstoneUntil` (epoch ms), `unknownAt` (epoch ms or null; the time the record transitioned to `UNKNOWN`, or null while the record has never been `UNKNOWN`; see §2.7), `manualConfirmation` (object or null; see §2.6), `supersedes` (string or null; the batch_id of the `UNKNOWN` record this batch replaces, or null if this batch does not supersede any record; see §2.6).
- **Retention formulas (exact, P1-1):** for a normal record, `expiresAt = createdAt + 10 min` and `tombstoneUntil = expiresAt + 10 min` (i.e. `createdAt + 20 min`). For an `UNKNOWN` record, `tombstoneUntil = max(createdAt + 20 min, unknownAt) + 24 h`, where `unknownAt` is the time the record became `UNKNOWN`. This guarantees both the original design intent (at least 20 minutes + 24 hours from creation) and a full 24 hours from the `UNKNOWN` transition, even for a batch that ran long before becoming `UNKNOWN` (a batch that ran 30 minutes before converting to `UNKNOWN` is kept until `unknownAt + 24 h`, not merely until `createdAt + 24 h 20 min`). All sections of this SPEC use this one formula (§2.7, §2.9).
- Validation on load: `format_version` must be 1; every record must have all required fields with the correct types; `batch_id` and `payload_hash` must be non-empty strings within their max lengths; duplicate `batch_id` values are rejected (the file is corrupt if a duplicate exists); a record whose status is `UNKNOWN` must have a non-null `unknownAt` (a number, not earlier than `createdAt`); any invalid value makes the file corrupt (§2.5). Unknown extra fields are ignored (forward compatibility), but a missing required field or a wrong type is corruption. (`unknownAt` is new in v2.3; the format version stays 1 because no implementation of this SPEC exists yet — there is no deployed file to migrate.)
- Per-record max size: 64 KB (a batch has at most 20 actions; a record larger than 64 KB is rejected at persist time and treated as a persist failure, §2.4). Total file cap: 512 KB (§2.7).
- The `result`, when present, must contain the full BatchResult: `batch_id`, `snapshot_id`, `status`, `payload_hash`, `replayed`, `results` (per-action `action_id`, `status`, `error`, `hash_before`, `hash_after`), `completed_action_ids`, `failed_action_id`, `stopped_at`, `stop_reason`. A replayed result must be semantically identical to the original HTTP response — status alone is not enough; `completed_action_ids` and the per-action results must all be restored.

**Atomic write and recovery:**
- The temp file is created in the **same directory** as the live file (so the rename stays on one filesystem).
- Write sequence: write the full new content to the temp file → flush → fsync the file descriptor → rename the temp file over the live file → fsync the directory entry if the platform allows it (best-effort; Android's Java API may not guarantee directory-entry durability, and that limit is recorded here rather than assumed away). **The guaranteed durability range must be determined by real-device power-loss-equivalent testing or fault injection (§5, P2-01) and recorded in the SPEC.** Until that test is done, the SPEC notes the limit: the file-body fsync is guaranteed by the API, but whether the rename itself survives a power loss is not guaranteed by the directory-entry fsync on this platform.

**Phone-side durability gate (P1-1, CONS-144):** the same durability principle as §2.9 applies to the phone-side persist. The phone-side storage method must be **demonstrated** to guarantee the required durability (survival across a device power loss / forced restart) in the actual deployment environment (the Galaxy A55) **before** `/batch` accepts batches. Until the demonstration is complete, `/batch` is refused with 503 `batch_store_durability_unverified` — the BatchRegistry must not execute any batch while its storage durability is unproven. The demonstration is the §5 real-device power-loss-equivalent test. If the file mode cannot guarantee durability on the device, the implementation must switch to a method that can (for example, a database with a durability guarantee, such as SQLite with `synchronous=FULL`); if no available method can guarantee it, `/batch` stays fail-closed. The verified state is recorded persistently (a durability-verified marker, written with the same atomic write); the marker records the storage method it was verified for, and if the storage method changes, re-verification is required before `/batch` resumes. "Directory fsync if the platform allows it" is implementation flexibility for the write procedure, never a relaxation of the durability requirement: the requirement is absolute, and the mechanism is chosen to meet it.
- The old live file is **never deleted before the rename**. The rename itself is the atomic switch: after a crash, either the old file or the new file is intact, never a half-written file.
- On start, a leftover temp file (or any incomplete file) is ignored and deleted. It is never treated as the record.
- A persist is successful only when write + flush + fsync + rename all succeed. If any step fails, the persist has failed (§2.4).
- If the rename itself fails, the old live file is untouched and remains the record; the failure is a persist failure (§2.4).

### 2.3 State machine and serialization (C3)

**Fixed order for every batch (no exceptions):**
1. Check the ID (under the Registry lock).
2. Persist `IN_PROGRESS`.
3. Execute — only after the persist succeeds.
4. Persist the result.
5. Respond.

**The Registry lock:** one lock (`BatchRegistry` lock) serializes the whole admission unit: ID lookup + payload-hash compare + new-record registration + `IN_PROGRESS` persist. The HTTP server has 4 workers, so two concurrent requests with the same ID must not both decide "new". The lock covers exactly that unit (and the result persist in step 4). Execution itself (step 3) runs outside the lock on the main thread, as today — but the record is already `IN_PROGRESS` and persisted before execution starts, so a concurrent same-ID request sees `IN_PROGRESS` and gets `status: "running"`.

**States:**

| Status | Meaning | When written |
|---|---|---|
| `IN_PROGRESS` | Execution has started (or is about to start). No result yet. | Before execution begins (step 2), persisted. |
| `COMPLETED` | All actions executed. | After execution, with the result (step 4). |
| `PARTIAL` | At least one action executed, then the batch stopped. | After execution, with the result (step 4). |
| `FAILED` | Zero actions succeeded. | After execution, with the result (step 4). |
| `UNKNOWN` | The outcome is not known. | On restart, any record still `IN_PROGRESS` becomes `UNKNOWN` (with `unknownAt` set to the conversion time). Never written during normal execution. |

**Replay rules (unchanged in shape, now enforced by the Registry):**
- A re-sent batch_id with a `COMPLETED`, `PARTIAL`, or `FAILED` record returns the stored result (`replayed: true`). No re-execution. The replayed result is the full stored BatchResult (§2.2).
- A re-sent batch_id with an `UNKNOWN` record returns `status: "unknown"`, `replayed: false`, with an explicit message. The batch is NOT re-executed.
- A re-sent batch_id with an `IN_PROGRESS` record (still running in this process) returns `status: "running"` (`replayed: true`).
- The same id with a different payload hash is 409. An id whose result expired is 410 until its tombstone lapses. Both unchanged.

### 2.4 Persist failure is fail-closed (C1, C9)

**IN_PROGRESS persist failure (C1):** if the step-2 persist fails (write, flush, fsync, or rename fails, or the record exceeds the per-record size cap), the batch is **not executed**. The server returns an explicit error (503, `persist_failed`, with a message that the batch was not executed and the client must not assume any action ran). The in-memory cache alone is never a basis for executing. If the persist state is unknown, that is also fail-closed. There is no compromise here: execution requires a successfully persisted `IN_PROGRESS` record.

**Result persist failure (C9):** if the step-4 persist fails, the batch has already executed, so the outcome is not "not executed". The record stays `IN_PROGRESS` in the file (or, if even that cannot be confirmed, the record is treated as `UNKNOWN` on the next load). A re-send returns `UNKNOWN`, never a re-execution. The HTTP response for the original request still returns the result (the caller already has it); the failure is logged, and the durability guarantee is lost for that batch only.

**Post-save crash vs result-save failure (C9):** these are distinguished. If the result was persisted and then the process crashed before the HTTP response was sent, a re-send returns the **saved result** (not `UNKNOWN`), because the result exists. If the result persist itself failed, a re-send returns `UNKNOWN`. The distinction is whether a `COMPLETED`/`PARTIAL`/`FAILED` record with a full result exists in the file.

**Persist failure generally:** any persist failure is logged with the batch_id and the failure cause. The failure never silently degrades to memory-only execution.

### 2.5 Startup states (C2)

On start, the Registry classifies the persistent file into exactly three states:

| Startup state | Condition | Behaviour |
|---|---|---|
| Normal records | The file loads and validates (§2.2). | Normal operation. Records still `IN_PROGRESS` become `UNKNOWN` (their outcome is unknown because the previous process did not finish them). |
| Normal empty | No file exists (the store was never initialized — a fresh install), or the file exists and validates as an empty record set with `recoveryPending: false`. | Normal operation as a fresh start. |
| Corrupt / unreadable | The file exists but fails validation (§2.2), or cannot be read. | **`/batch` is fail-closed.** The Bridge (HTTP server, `/health`, `/state`, read-only endpoints) starts normally, but `/batch` is refused (503, `batch_store_unavailable`) until the record is safely restored. A corrupt record is never treated as an empty record. |

Separation: Bridge startup and batch-function startup are distinct. A corrupt batch store must not prevent the Bridge from starting (health and read-only paths stay up), but it must prevent any batch from executing, because executing without knowing which IDs already ran risks re-execution.

**Recovery from corruption (P1-2):** a backup file (`batch_records.json.bak`, the last known-good file) may be used for recovery, but **only by an explicit operator action — never automatically at startup**. When the live file is corrupt, `/batch` stays fail-closed (503 `batch_store_unavailable`) until the operator deliberately triggers a restore. There is no automatic restore: an automatic restore could silently bring back a one-generation-old record set and lose the most recent batch's record, which would re-open a re-execution path if the client ever re-sent that ID.

- **What the .bak is:** on each successful persist, before the rename that replaces the live file, the current live file is copied to the backup. The backup is therefore **at most one persist behind** the live file. The backup is written atomically (write to a temp file in the same directory, flush, fsync, rename over the old `.bak`), so a failed backup write never corrupts the previous backup.
- **If the backup write fails:** the failure is logged, and the main persist proceeds. The backup is a recovery convenience, not part of the durability guarantee for the current batch — the live-file rename is what makes the current batch durable. A failed backup write does not fail the main persist (it is not fail-closed), because failing the persist would refuse a batch whose record could have been written safely.
- **Status conversion on restore:** when the backup is restored, records in a terminal state with a valid result (`COMPLETED`, `PARTIAL`, `FAILED`) are kept as-is, because their outcome is determined and their result is complete. Every other record (`IN_PROGRESS` and any existing `UNKNOWN`) is converted to `UNKNOWN`, because its outcome is not provably complete. The conversion rule is exactly this: **all records except `COMPLETED` / `PARTIAL` / `FAILED` with a valid result become `UNKNOWN`**. A record converted to `UNKNOWN` at restore time gets `unknownAt` set to the restore time; a record that was already `UNKNOWN` keeps its existing `unknownAt`.
- **The missing-batch gap:** a batch executed after the backup was written is absent from the restored record set. That batch's ID is not in the store at all, so a re-send of it would be treated as new. This gap is closed by the combination of (a) operator-explicit restore only, (b) the VM-side permanent batch_id reuse ban (§2.9), which makes a re-send unreachable in correct operation, (c) the recovery-verification gate below, and (d) logging: the restore (including which backup was used, its age, and that batches executed after it may be missing) is logged, and the operator must check the phone for any batch executed after the backup was written before allowing new work. The restore does not by itself guarantee that no batch is missing; it guarantees only that no restored record claims an outcome it cannot prove.
- **Recovery-verification gate (P1-2):** after a restore, the Registry enters the recovery-verification state (`recoveryPending: true`, persisted in the file's top level, §2.2). While `recoveryPending` is true, **`/batch` is refused for every request, including new batches, with 503 `batch_store_recovery_pending`**. The gate exists because the operator might otherwise allow a new batch before checking the phone's execution history, and the same operation could then run again under a new ID. The operator must check the phone's execution history (what actually ran after the backup was written), then record the verification completion through an explicit management operation (for example `POST /batch/recovery_complete`, with the operator's identity), which sets `recoveryPending: false` and records `completedAt` / `completedBy` in `recoveryInfo`. Only then does `/batch` resume. The gate is persisted in the file, so a Bridge restart does **not** clear it — the gate survives until the operator completes verification.
- **The gate also applies to a deliberate store clear / re-initialization (P1-2, CONS-141):** if no backup exists or the backup is also corrupt, the operator may clear the store deliberately — but the clear **also** sets `recoveryPending: true` (persisted). "Clearing the store" and "confirming the execution history is empty" are two different operations: clearing the store does not prove that no batch recorded in it had executed. After a clear, `/batch` stays refused with 503 `batch_store_recovery_pending` until the operator checks the phone's execution history and records verification completion through the same explicit management operation. The clear itself is logged, and the verification completion is logged separately. There is no path that resumes `/batch` after a corrupt store without the operator first confirming the phone's execution history.
- **Atomic clear procedure (P1-A, CONS-142):** the clear and the gate setting are **one atomic state transition**. The clear must never delete the existing store file first. The procedure is: (1) build the new store content — `{"format_version": 1, "records": [], "recoveryPending": true, "recoveryInfo": {"clearedAt": <server time>, "reason": "store_clear", "note": <operator note>}}`; (2) write it to a temp file in the same directory, flush, fsync; (3) rename the temp file over the live file (the atomic switch, §2.2); (4) fsync the directory entry if the platform allows it (best-effort). Only after the rename succeeds is the clear complete. Crash points: if the process stops **before** the rename, the old file (corrupt) is still there, so startup sees "Corrupt / unreadable" and `/batch` stays fail-closed with 503 `batch_store_unavailable`; if it stops **after** the rename, the new file has `recoveryPending: true`, so `/batch` is refused with 503 `batch_store_recovery_pending`. In neither case does a crash produce "Normal empty". The "Normal empty" startup state therefore means only that the store was never initialized (a fresh install) — because the clear procedure never leaves the system in a "no file" state. If the clear's own write fails, the old file remains and `/batch` stays fail-closed; the operator retries the clear. The clear does **not** touch the `.bak` file: the `.bak` is only ever read by an operator-explicit restore, which always sets the gate, so leaving it in place creates no bypass. (Limitation, stated explicitly: if the app's private files are deleted externally — for example a full app-data wipe — the system cannot distinguish that from a fresh install. That is outside the Bridge's control; it is the same as reinstalling the app.)
- If no backup exists or the backup is also corrupt, `/batch` stays fail-closed until an operator clears the store deliberately (a deliberate clear is itself logged). The clear sets `recoveryPending: true` (see the gate above), so `/batch` remains refused with 503 `batch_store_recovery_pending` until the operator verifies the phone's execution history and records completion — the clear alone does not resume `/batch`.

### 2.6 UNKNOWN handling and manual confirmation (C5, P2-01)

- A re-sent `UNKNOWN` batch_id returns `status: "unknown"` and is never re-executed.
- `UNKNOWN` **never auto-recovers**. It does not become executable again on its own, and it is never silently converted back to a runnable state.
- **Manual confirmation:** when the operator checks what actually happened on the phone, the confirmation is recorded in the `UNKNOWN` record's `manualConfirmation` field (`confirmedAt`, `confirmedBy`, `confirmedVia`, `outcome` — one of `executed` / `not_executed` / `partial`, plus a free-text `note`). The record stays `UNKNOWN` (its status does not change); the confirmation is an annotation on it, not a state transition. **Recording means (P2-1):** the confirmation is recorded through a dedicated management endpoint (for example `POST /batch/confirm` with the batch_id and the confirmation fields), which updates the record under the `BatchRegistry` lock and persists it with the same atomic write as any other persist (§2.2). If that persist fails, the confirmation is not recorded and the operator is told to retry; the record stays `UNKNOWN` without the annotation. Manual file editing is **not** a supported recording means — it bypasses the lock and risks corrupting the store. **Memory / persist consistency:** the in-memory record is updated only after the persist succeeds; on a persist failure the in-memory state is rolled back (or never updated), so memory and the file never disagree — a confirmation that exists only in memory and not in the file must never be visible. **Endpoint auth and the three-way distinction (P2-1, CONS-141):** the management endpoint is authenticated and authorized (not open). Three things are recorded separately and must not be conflated: (a) the **authenticated subject** — the client identity that executed the management operation (recorded in `confirmedVia`); (b) the **human confirmer** — the person who checked the phone's execution history (recorded in `confirmedBy`, as an attestation supplied through the client, not as an authenticated identity); (c) the **record time** — `confirmedAt` is set by the server at processing time (client-supplied timestamps are ignored). The VM client's authentication proves only that the VM is a legitimate client; it does not prove the identity of the human who checked the phone. This distinction holds even in the interim operation before SPEC-AUTH-001 is adopted. The exact authorization tier is defined in SPEC-AUTH-001 (C-02); until that SPEC is adopted, the endpoint accepts only the VM's authorized client. This endpoint never returns an `UNKNOWN` record to an executable state, so the issue here is the trustworthiness of the audit record, not re-execution.
- **Re-operation:** if a new operation is needed after a manual confirmation, it is issued as a **new batch_id** (a separate, confirmed operation). The new record carries a `supersedes` field naming the old `UNKNOWN` batch_id, so the link between the old record and the new operation is traceable. The old `UNKNOWN` record is never re-executed and never reused. **Supersedes referential integrity (P2-2):** `supersedes` must reference an existing `UNKNOWN` record; it must not be the same ID as the new batch itself; a reference to a nonexistent record, a self-reference, or a reference to a record that is not `UNKNOWN` is rejected with 400. The reference validation happens **inside the `BatchRegistry` lock**, so the referenced record cannot be deleted between validation and registration. A re-operation is issued only after a manual confirmation (a human checked the phone and approved the new operation as a separate, confirmed operation) — never automatically.
- **VM client on UNKNOWN:** MUST NOT re-send the same batch_id. MUST NOT auto-issue a new batch_id. MUST report outcome-unknown to the operator with the batch_id and the actions, so a human checks the phone and decides.

### 2.7 Retention, capacity, and eviction (C4, C5, C6)

- Result lifetime 10 minutes, tombstone 10 minutes (20 minutes total). Unchanged from `BATCH_TTL_MS` / `BATCH_TOMBSTONE_MS`.
- After the tombstone lapses, the record is purged (on load and lazily on insert, as today). A re-send after that is treated as a new batch (today's 410-then-new behaviour is unchanged).
- **IN_PROGRESS is never evicted while alive (C4).** A record in `IN_PROGRESS` is exempt from every purge and capacity rule for as long as its execution is in flight. This holds even if the HTTP request deadline (45 s) has passed — the AccessibilityService-side work may still be running, and the record must survive until the execution reports back (as a result or, on restart, as `UNKNOWN`).
- **UNKNOWN retention (C5):** an `UNKNOWN` record is kept for the full 20-minute retention (same as a result), and then for a further 24 hours as a safety record. Its `tombstoneUntil` is `max(createdAt + 20 min, unknownAt) + 24 h` (§2.2), where `unknownAt` is the time the record became `UNKNOWN`. This guarantees a full 24 hours from the `UNKNOWN` transition even for a batch that ran long before converting (for example, a batch that ran 30 minutes before a restart converts to `UNKNOWN` at `unknownAt = createdAt + 30 min` and is kept until `unknownAt + 24 h`, not merely until `createdAt + 24 h 20 min`). It is purged only after that. If the same ID is re-sent after the `UNKNOWN` record is purged, it is treated as a new batch — but only after the full retention has elapsed, and the purge is logged. The 24-hour window is the safety margin: it covers the realistic time for a human to notice and confirm an `UNKNOWN` batch. **The permanent protection against a late re-send after the retention expires is the VM-side permanent batch_id reuse ban (§2.9, P1-01), not the retention itself.** The server does not by itself guarantee permanent prevention.
- **Capacity (C6):** at most 100 records, total file at most 512 KB. Purge order when the cap is reached: (1) records past their tombstone (expired), (2) `UNKNOWN` records past their `tombstoneUntil` (§2.2). A live `COMPLETED` / `PARTIAL` / `FAILED` record and a live `IN_PROGRESS` record are **never evicted** to make room. If no safely-deletable record exists when a new batch arrives, the new batch is **rejected with 503** (`batch_store_full`), and the existing safety records are kept. Capacity shortage refuses new work; it never deletes safety records.
- The 10 + 10 minute periods are kept. Note: for the 20-minute reuse to be safe, the client-side resend deadline must be consistent with it (the VM must not re-send an ID after 20 minutes expecting dedup). The VM retry policy is out of scope for this SPEC, but the consistency requirement is recorded here.

### 2.8 Lifecycle: service restart, disconnect, worker timeout

The Registry's state is keyed to the **process**, not to a single service connection:

- **BridgeService restart:** the Registry is reloaded from the file (§2.5). Records still `IN_PROGRESS` become `UNKNOWN` (the previous process did not finish them). No in-flight record is silently reused.
- **AccessibilityService disconnect / reconnect:** a disconnect does not change any record's state. A batch that was executing when the service disconnected stays `IN_PROGRESS` until the execution reports back or the process restarts (in which case it becomes `UNKNOWN`). A reconnect does not resume or re-run a batch.
- **HTTP worker stop / timeout:** if the HTTP worker that accepted a batch stops or times out (45 s deadline), the batch's record stays `IN_PROGRESS` (the service-side work may still be running). The worker timeout does not cancel the record and does not make the ID reusable. A re-send while the record is `IN_PROGRESS` gets `status: "running"`.
- In all three cases, the rule is the same: a record leaves `IN_PROGRESS` only by a persisted result or by becoming `UNKNOWN` on restart. It is never silently reset.

### 2.9 Batch_id generation and the permanent reuse ban (P1-01, CONS-134)

**The problem:** after an `UNKNOWN` record is purged (§2.7), a late-arriving old request with the same batch_id would be treated as a new batch and executed. The server-side retention alone cannot prevent this permanently, because no finite retention covers an arbitrarily late re-send.

**The rule (client-side, permanent):** the VM client **MUST NEVER reuse a batch_id**. Each batch gets a fresh, unique batch_id. The VM MUST NOT re-send the same batch_id after any failure, restart, or timeout. If a batch's outcome is unknown, the VM reports it and a human decides; a re-operation uses a NEW batch_id. This is a permanent client-side invariant, not a time-limited one.

**The rule, extended to logical batches (C-01-15, CONS-140):** not re-sending the same ID is not enough. The VM must also **never automatically re-issue the same logical batch under a new ID**. A *logical batch* is the operation the user intends to perform (a specific set of actions with a specific purpose); a batch_id identifies one transmission attempt of a logical batch. Once the VM has started sending a logical batch, it must not automatically generate a new batch_id for that same logical batch — not after a lost response, not after a timeout, not after a client restart, and not after restoring a persistent queue. The phone cannot distinguish a re-issued logical batch from a genuinely new one (the IDs differ, so the phone accepts it as new), so this protection is entirely client-side. A new batch_id for the same logical operation may be issued **only** when a human has checked the phone state and explicitly approved it as a new operation (after a manual confirmation, §2.6). This applies whenever the outcome is undetermined — `UNKNOWN`, a lost response, a timeout, a communication failure, or a client restart — not only to `UNKNOWN`.

**Client-side tracking:** to enforce this, the VM client keeps a persistent record of logical batches it has sent (an outbox that survives client restarts), with each logical batch's identity, its batch_id, and its outcome state (sent / result received / outcome unknown). A logical batch whose outcome is undetermined stays in that state until a human decides; the client's retry logic must never silently regenerate it with a new ID. If a future client change ever re-issues a logical batch automatically, that change must be reviewed as a safety regression, because it would re-open the double-execution path that this SPEC exists to close.

**Fixed outbox send order (C-01-15, CONS-141):** the outbox record must be persisted **before** the first network send. The order is fixed: (1) generate the logical batch's persistent ID; (2) register the logical batch and its batch_id in the outbox; (3) confirm the outbox persist succeeded; (4) only then allow the network send; (5) after receiving the result, persistently update the outbox state. If the outbox persist fails, the batch must **not** be sent. If the outbox is corrupt, missing, or unreadable, sending stops (**fail-closed**) — the outbox must never be treated as an empty queue. This order covers not only a lost response after send and a VM restart, but also a crash just before or just after the outbox write and just before or just after the network send: in every case the logical batch is either recorded before it could have executed, or never sent. The phone-side BatchRegistry and the VM-side outbox are one safety mechanism, not two independent ones: however robust the phone-side persistence is, it cannot prevent a double execution if the VM forgets what it sent and re-issues it under a new ID.

**Durable commit (P1-B, CONS-142):** "persist succeeded" means a **crash-recoverable durable commit** — the record has reached stable storage and survives a host power loss or forced restart, not merely the OS page cache. A write that only reaches the OS buffer is **not** a successful persist. The mechanism depends on the outbox storage, and the SPEC requires the durability, not the engine: if the outbox is a file, the write must be an atomic write (temp file + flush + fsync of the file descriptor + rename over the live file + directory-entry fsync if the platform allows it, the same pattern as §2.2); if the outbox is a database, the write must be a committed transaction with a durability guarantee (for SQLite, a transaction with `synchronous=FULL`, or WAL with a synchronous commit). Whichever mechanism is chosen, its durability must be verified by a crash test (kill the VM process or the host after the write and confirm the record survives; see C-01-15).

**Storage-method durability gate (P1-1, CONS-143):** the chosen storage method must be verified to guarantee the required durability (survival across host power loss / forced restart) in the actual deployment environment **before** sending is allowed with it. If the file mode cannot guarantee it — for example, directory fsync is unavailable and the rename's durability cannot be confirmed — file mode must **not** be used; choose a database mode (SQLite with `synchronous=FULL` or WAL with a synchronous commit) that can guarantee it. If no available method can guarantee it, sending is **fail-closed** (no sending at all). "Directory fsync if the platform allows it" remains as implementation flexibility for the write procedure, but it never relaxes the durability requirement itself: the requirement is absolute, and the mechanism is chosen to meet it. The implementation must record its chosen method and why it guarantees durability in the deployment environment, and C-01-15's crash test verifies the chosen method's durability in practice. (The same principle applies to the phone-side persist in §2.2: its durability is established by the real-device power-loss-equivalent test in §5, and if that test shows the rename does not survive, the implementation must choose a method that does or fail-closed.)

**Persistent init marker and startup decision table (P1-2, CONS-143):** the client records its initialized state in a **persistent init marker** — a separate file (for example `outbox_initialized`) written with the same durable commit (atomic write + fsync) and never deleted by the client. Initialization runs in this order: (1) create the outbox file (empty, with a format header) via atomic write + fsync; (2) create the marker file (with the creation time and format version) via atomic write + fsync. Because the marker is created **after** the outbox, "marker exists" implies "outbox was created". At startup, the client decides by this table:

| Marker | Outbox file | Decision |
|---|---|---|
| Exists | Exists and readable | Normal operation (initialized). |
| Exists | Missing, corrupt, or unreadable | **Fail-closed** — sending stops. The client was initialized and its outbox is lost. |
| Missing | Missing | **Requires explicit operator initialization** — the client does **not** auto-initialize (P1-2, CONS-144). See below. |
| Missing | Exists and empty | Initialization stopped midway (the outbox was created but the marker was not) — complete initialization by creating the marker, then start with an empty outbox. No sends could have happened before initialization completed, so completing it is safe. |
| Missing | Exists and non-empty | **Fail-closed** — contradictory state. The marker was lost after sends happened (the outbox has records, so initialization must have completed). The client must not guess that it is uninitialized. |

**Joint disappearance (P1-2, CONS-144):** the marker and the outbox live on the same storage, so they are **not** independent failure domains. "Both missing" is true not only for a genuinely fresh client, but also when both files are lost together (a storage failure, a data-directory loss, a VM snapshot rollback). Treating "both missing" as automatically uninitialized would lose the record of previously sent logical batches and let the client re-issue them under new IDs. Therefore, when both are missing, the client **refuses to send (fail-closed)** until the operator performs an **explicit initialization operation** (for example, a management command that records the initialization). Before initializing as fresh, the operator must verify from external records — the phone's execution history, or the operator's own logs — that **no logical batch was sent from this client**. If that cannot be verified, the client must **not** be initialized as fresh; instead the outbox must be recovered from a backup, or the situation must be treated as a recovery (undetermined batches are never auto-reissued). The initialization operation is logged and records the operator's attestation (who, when, and the basis — for example "fresh install" or "loss accepted after checking the phone's history"). If an independent persistent state exists — one that does not disappear together with the outbox (for example, a record in a separate storage domain) — it may be used to confirm that the client is genuinely fresh; otherwise, explicit operator initialization is required. The marker itself must be durable (the same atomic write + fsync as the outbox); if the marker and the outbox contradict each other, the client fails closed. The marker is never deleted by the client, and neither is the outbox file.

**Startup handling of ambiguous outbox records (P1-B, CONS-142):** at startup, an outbox record that was recorded but whose send state is unknown (recorded before the send, or sent with an unknown outcome) is treated as **undetermined** and is **never automatically re-issued**. This is safety over availability: an ambiguous record blocks automatic reissue, and a human decides. Whether the client is initialized, and what a missing outbox file means, is decided by the init-marker table above — never by guessing from the outbox file alone.

**Batch_id generation:** the VM generates each batch_id as a UUID v4 (122 random bits). A fresh UUID is generated per batch. Because the ID is random (not a counter or a timestamp), a VM restart cannot produce a duplicate ID — there is no counter to reset and no sequence to replay. Accidental collision is negligible (2^-122 per pair). The server validates the batch_id format (max 128 chars, non-empty; a UUID v4 is 36 chars) and rejects a malformed ID with 400.

**Server-side expired-ID handling:** the server's `UNKNOWN` retention (§2.7, `tombstoneUntil = max(createdAt + 20 min, unknownAt) + 24 h`) is a safety net for re-sends within that window. After the retention expires and the record is purged, a re-sent ID is treated as a new batch (today's behaviour for an unknown ID). This is safe **only because** the client ban makes a late re-send unreachable in correct operation. The server does **not** by itself guarantee permanent re-execution prevention; the guarantee is the combination of the client-side permanent reuse ban and the server-side retention. That distinction is explicit: do not claim the server alone prevents re-execution forever.

**Enforcement:** the VM client code generates a fresh UUID v4 per batch and never stores a batch_id for reuse. The rule is recorded here and in the VM client's retry policy (a stated design constraint in the client, not just a convention). If a future client change ever reuses an ID, that change must be reviewed as a safety regression, because it would re-open the late re-send path.

### 2.10 What does NOT change

- The `/batch` request and response shapes are unchanged, except for the new `status: "unknown"` value and the new 503 errors (`persist_failed`, `batch_store_unavailable`, `batch_store_full`, `batch_store_recovery_pending`, `batch_store_durability_unverified`). An `UNKNOWN` response carries no `results` array, only the batch_id, status, and message.
- `protocol_version` stays 1. No new protocol version.
- The 20-action cap, the 45 s request deadline, and the tree_hash entry check are unchanged.
- The batch execution itself (`runBatchInternal`, `executeAction`) is unchanged; only the registry around it changes.
- The notification rule ("notify before operation") is user visibility only and is not a substitute for this SPEC. See decision 102 and the C-04 SPEC for the role separation.

## 3. Acceptance criteria

- [ ] C-01-1: crash immediately after batch execution (before the result write) — verify `UNKNOWN` on re-send, no re-execution.
- [ ] C-01-2: crash during batch execution — verify `UNKNOWN` on re-send, no re-execution.
- [ ] C-01-3: concurrent send of the same batch_id — verify one executes, the other gets `running`.
- [ ] C-01-4: same batch_id re-sent after a restart — verify the stored result is replayed, no re-execution.
- [ ] C-01-5: dedup at capacity — verify a live record is never evicted when the cap is reached.
- [ ] C-01-6: `IN_PROGRESS` persist failure — verify no operation starts at all (the batch is rejected with an explicit error).
- [ ] C-01-7: corrupt JSON on start — verify `/batch` is refused and the existing record is not treated as empty.
- [ ] C-01-8: crash immediately before the rename — verify the existing file is preserved (old or new, one intact file).
- [ ] C-01-9: concurrent send of the same ID — verify the side effect happens at most once. (C-01-3 and C-01-9 test the same concurrent-send scenario from two angles and are both kept: C-01-3 verifies the **response** — one executes, the other gets `running`; C-01-9 verifies the **side effect** — checked externally on the phone, the action happened at most once.)
- [ ] C-01-10: `UNKNOWN` under capacity pressure — verify deleting an `UNKNOWN` record does not make its ID re-executable (retention + new-batch rejection).
- [ ] C-01-11: result persist failure — verify the batch is treated as `UNKNOWN`, not auto-re-executed.
- [ ] C-01-12: state restore after a restart — verify every field keeps its original meaning (full result, not just status).
- [ ] C-01-13: service reconnect — verify an old execution and a new one do not race.
- [ ] C-01-14: crash after the result is saved but before the HTTP response — verify the re-send returns the saved result (not `UNKNOWN`).
- [ ] C-01-15: VM-side batch_id non-reuse and logical-batch non-reissue — verify the VM client never reuses a batch_id (the client generates a fresh UUID v4 per batch, and after a failure, a restart, or a timeout it does not re-send the same ID), **and** never automatically re-issues the same logical batch under a new ID while its outcome is undetermined. The test covers a lost response after send, a timeout, a VM restart, and a persistent-queue restore, and verifies that the same logical operation is not re-sent under a new ID in any of them (verified by a client-side test that records every logical batch and every batch_id the client emits across those scenarios and asserts that no undetermined logical batch is re-issued, plus a code read of the client's retry path). On `UNKNOWN` or any undetermined outcome the client reports to the operator and does not auto-issue a new batch_id; a new ID for the same logical operation is issued only after a human checks the phone and explicitly approves it. The test also covers the outbox persist order: crashes just before the outbox write, just after the outbox write, just before the network send, and just after the network send must never produce a re-issued logical batch under a new ID; an outbox persist failure must prevent the send, and a corrupt, missing, or unreadable outbox must stop all sending (fail-closed, never treated as an empty queue). **Durable commit (P1-B):** verify the outbox persist is a crash-recoverable durable commit — kill the VM process (or the host, where feasible) after the outbox write and confirm the record survives and the logical batch is not re-issued under a new ID; verify the write uses the required mechanism (atomic write + fsync for a file, or a committed transaction with a durability guarantee for a database). At startup, verify an outbox record whose send state is unknown is treated as undetermined and is never automatically re-issued. **Storage-method durability gate (P1-1):** verify the implementation records its chosen storage method and why it guarantees durability in the deployment environment, and verify sending is disabled (fail-closed) when the chosen method cannot guarantee the required durability (for example, file mode without a confirmable directory fsync and no database alternative). **Init marker (P1-2):** verify every row of the startup decision table — marker + readable outbox (normal), marker + missing/corrupt outbox (fail-closed), neither (explicit operator initialization required — the client does **not** auto-initialize, and sending is refused until the operator performs the explicit initialization operation; verify the operation is logged and records the operator's attestation), marker missing + empty outbox (initialization completed), marker missing + non-empty outbox (fail-closed). **Joint disappearance (P1-2, CONS-144):** verify that when both the marker and the outbox are missing, the client refuses to send until the explicit operator initialization is performed, and verify the operator must confirm from external records that no logical batch was sent before initializing as fresh.
- [ ] C-01-16: recovery-verification gate — after a backup restore, verify `/batch` is refused with 503 `batch_store_recovery_pending` for every request (including new batches) until the operator completes verification through the explicit management operation; verify the gate survives a Bridge restart (it is persisted in the file); after the verification operation, verify `/batch` resumes. The same gate applies after a deliberate store clear / re-initialization: verify the clear sets `recoveryPending: true` and `/batch` stays refused until verification completes. **Atomic clear (P1-A):** verify the clear procedure at each crash point — a crash before the rename leaves the old (corrupt) file in place and `/batch` stays fail-closed with 503 `batch_store_unavailable`; a crash after the rename leaves the new file with `recoveryPending: true` and `/batch` is refused with 503 `batch_store_recovery_pending`; no crash point during the clear produces "Normal empty" or resumes `/batch` without verification.
- [ ] C-01-17: `unknownAt` retention — verify a batch that runs long (still `IN_PROGRESS` past the 20-minute mark) and then converts to `UNKNOWN` on restart gets `tombstoneUntil = unknownAt + 24 h` (a full 24 hours from the conversion, not merely `createdAt + 24 h 20 min`), verified by reading the stored record's computed `tombstoneUntil` after the conversion.
- [ ] C-01-18: phone-side durability gate — verify `/batch` is refused with 503 `batch_store_durability_unverified` until the phone-side storage durability is demonstrated by the §5 real-device power-loss-equivalent test, and resumes only after the durability-verified marker is recorded; verify the marker records the storage method it was verified for, and that changing the storage method requires re-verification before `/batch` resumes; verify that if the file mode cannot guarantee durability on the device, the implementation switches to a method that can, and that if no method can, `/batch` stays fail-closed.

## 4. Failure behaviour (summary)

- Persist failure on `IN_PROGRESS`: the batch is not executed; 503 `persist_failed`; logged; fail-closed. (C1)
- Persist failure on the result: the record stays `IN_PROGRESS` / becomes `UNKNOWN`; the original caller still gets its result; the failure is logged; no auto-re-execution. (C9)
- Corrupt / unreadable file on start: `/batch` fail-closed (503 `batch_store_unavailable`); the Bridge and read-only endpoints start normally; recovery via backup is allowed only by an explicit operator action (never automatically), with `UNKNOWN` conversion of non-terminal records and logging. (C2)
- Recovery-verification pending: after a backup restore or a deliberate store clear / re-initialization, `/batch` is refused for every request with 503 `batch_store_recovery_pending` until the operator checks the phone's execution history and records verification completion through the explicit management operation; the gate survives a restart. (C-01-16)
- Capacity reached with no safely-deletable record: new batches are rejected with 503 (`batch_store_full`); existing safety records are kept. (C6)
- In all failure cases the Bridge keeps serving (except `/batch` when its store is unusable); only the durability guarantee degrades, and the degradation is logged.

## 5. Verification (tests)

Kohaku (CONS-131, CONS-133) requires, at minimum, C-01-1 through C-01-18 (§3). Where a live crash test is impractical, a code-level test that actually kills and restarts the process is acceptable — a unit test that only calls the functions without a restart does not verify this SPEC.

The minimum kill-and-restart procedure: stop the Bridge process; confirm it has fully exited; restart the Bridge; re-send the same batch_id; confirm no re-execution, both from the visible side effect on the screen and from the stored record. Real-device testing is recommended. Fault injection is also required: explicitly cause write failure, rename failure, JSON truncation, and capacity overflow. The test actions must be safe actions whose double execution is externally distinguishable; do not use real banking or payment operations for testing.

**Directory fsync / power-loss-equivalent testing (P2-01, CONS-134; P2-01, CONS-145):** the guaranteed durability range of the rename must be determined by real-device testing. At minimum, a test that kills the process at the rename point (immediately before and immediately after the rename) and confirms that either the old file or the new file survives intact (never a half-written file). **The phone-side durability gate must not be released based only on process-kill testing. A real-device power-loss-equivalent test on the Galaxy A55 is required to demonstrate the durability of the selected storage method. If the test cannot be performed or the result cannot establish durability, /batch remains fail-closed.** The result (what is guaranteed and what is not) is recorded in the SPEC (§2.2). Until that test is done, the SPEC states the limit explicitly rather than claiming a guarantee it cannot prove.
