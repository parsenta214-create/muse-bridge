## 0. Goal

Turn off only Muse Bridge's accessibility service with one tap on a home-screen shortcut. When you are done using it and want accessibility off (to avoid detection by banking apps, or to keep an unused feature off), you should not have to open several levels of the Settings screen. Turning it back on remains a manual operation in Settings, as before (an Android limitation).

## 1. Decisions (D1–D8)

- D1: Use the **shortcut approach**. Do not do automatic turn-off linked to Bridge off. the System Development Lead's choice (2026-11-08 09:09 +07). The linked approach was set aside because it would add the hassle of going to the Settings screen every time you use it next. If a future version lets Settings choose on/off, that is a separate spec.
- D2: The turn-off mechanism is **`AccessibilityService.disableSelf()`**. A service can turn itself off (API 24+, available with minSdk 30). The caller is `BridgeAccessibilityService.getInstance()` (set in `onServiceConnected`, reset to null in `onDestroy`).
- D3: **Off only**. Do not create a shortcut to turn it back on. An app cannot turn its own accessibility on (an Android limitation). Turning it back on is a manual operation in Settings → Accessibility → Installed apps → Muse Bridge.
- D4: The shortcut does **not stop the server**. It turns off only accessibility. The server keeps running, but screen operations fail with `ACCESSIBILITY_DISABLED` (existing behavior). Stopping the server is done with the existing stop button (app / widget / tile).
- D5: Shortcut creation is done from **a button inside the app**. `ShortcutManager.requestPinShortcut()` is called on a **worker thread**; the user confirms in the system's pin confirmation dialog, and the shortcut is placed on the home screen. Confirmation of the creation is left to the system dialog. `PinRequestManager` (an Application-scoped static singleton) holds four independent states: (1) UI state `uiState` (IDLE / REQUESTING / WAITING_CONFIRMATION; the button's enabled/disabled state mirrors `uiState == IDLE`. The old `COMPLETED` state is abolished and merged into IDLE), (2) worker state `workerRunning` (true / false), (3) unresolved-request state `unresolvedState` (NONE / REQUESTING_UNRESOLVED / CONFIRMATION_UNRESOLVED), (4) lifecycle record `pauseObserved` / `resumeObserved` (recorded for reference only). All reads, writes, and transitions of the state are serialized on the main thread. When a fatal VM `Error` occurs in the worker, the worker's finally notifies the main thread of an Error-specific recovery event. The recovery event carries an outcome field (`KNOWN_TRUE` / `KNOWN_FALSE` / `KNOWN_EXCEPTION` / `UNKNOWN`). The worker keeps a local variable holding the known outcome, set when the API returns or the exception is caught, before attempting the post (in addition to `resultEventPosted`). The worker keeps a local variable `resultEventPosted` (initial value false) to track whether the normal result event has been posted. A normal true/false sends only the normal result event, an `Exception` sends only the normal exception event, and an `Error` sends only the Error-specific recovery event. The finally block sends the Error-specific recovery event only when `resultEventPosted == false`. `PinRequestManager` applies the carried outcome on the main thread: `KNOWN_FALSE` applies the false path immediately; `KNOWN_TRUE` applies the true path; `KNOWN_EXCEPTION` applies the false path; `UNKNOWN` (a true `Error`, no result) sets `workerRunning = false`, returns `uiState` to `IDLE` if it is `REQUESTING`, and — because it is unknown whether the API accepted the request — moves `unresolvedState` to `CONFIRMATION_UNRESOLVED` and starts the 60s release timer. An `Error` is not caught; it is rethrown. If the Error-specific recovery event's own post fails, the terminal state is defined as follows: if the main thread is no longer alive (the usual cause of post failure), the process is terminating and a recreated process starts at `uiState = IDLE`, `workerRunning = false`, `unresolvedState = NONE` (the same as the process-death case); if the main thread is alive, the already-scheduled 30s `REQUESTING` timeout still fires and converges the state to the Error-recovery terminal state (see §3.1 step 8); if the timeout has already fired, the re-armed guard converges it. No in-memory state recovery is guaranteed when the process ends. `onPause → onResume` is recorded only as reference information for recovery, and unresolved requests are released by timeout only. When an Activity is recreated, the existing request state is carried over.
- D6: **No new permissions, no new drawables, no new components**. `ShortcutManager` needs no permission. The icon reuses the existing `R.drawable.ic_tile`. The shortcut intent is an explicit intent to MainActivity; no new exported component is created. The only manifest change allowed is adding the `fullBackupContent` attribute and the `dataExtractionRules` attribute for token backup exclusion (per the P2-02 decision. D6 was revised in v5, and dataExtractionRules was added in v6).
- D7: **The disable intent carries an in-app token**. The token is a UUID generated only once, on first use, and stored in the app's dedicated SharedPreferences file `a11y_off_token_prefs` (other apps cannot read it). It is embedded as an intent extra when the shortcut is created. MainActivity executes the disable only when the action matches and the extra token matches the stored value. If the stored value or the extra is null or an empty string, it is not treated as a match, and the disable is not executed. The token must not be output in exception messages or debug logs. An intent that does not match (including one sent from another app) is ignored silently (no toast, no disable). Because the action name alone is not authentication, this token is the breakwater against external launches. The token does not change when the shortcut is recreated (the stored value is reused), so old shortcuts keep working. Saving is done with `commit()` (synchronous, returns success/failure), and the creation request is sent only after confirming the save succeeded. If the save fails, do not create. The token is treated as credentials and must not be output to logs. This is not a mechanism for verifying the calling app's identity; it is a Bearer Token scheme that accepts only intents carrying the secret. A replay by a third party that has obtained the token cannot be prevented. Compromise of the trust boundary outside the app, such as a rooted device or a launcher compromise, is out of scope. The default launcher is a trusted principal that handles intents containing the token, and it is placed inside the trust boundary. Use of an untrusted launcher is out of scope. The token is device-specific credentials and is excluded from backup / device-transfer restore (stored in the dedicated SharedPreferences file `a11y_off_token_prefs` (real file `a11y_off_token_prefs.xml`) and excluded by the backup-exclusion rule). Exclusion is done in both fullBackupContent (Android 11 and earlier) and dataExtractionRules (Android 12 and later), and in dataExtractionRules it is excluded from both cloud-backup and device-transfer. Because targetSdk is 34, dataExtractionRules is the primary mechanism. After a restore, the token does not exist, so old shortcuts stop working (recreate them from the button inside the app). Actual backup behavior differs by Android version, so check it against the build configuration at implementation time. No token revocation / reissue mechanism exists in the current spec.
- D8: **Fix the shortcut intent flags**: `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TOP | FLAG_ACTIVITY_SINGLE_TOP`. MainActivity has no launchMode specified (standard), so without flags a new instance would be created every time.

## 3. Design

### 3.1 Creating the shortcut

1. Press the MainActivity button "Create a shortcut to turn off accessibility" (Japanese: `補助機能オフのショートカットを作る`). The request state is held by `PinRequestManager` (an Application-scoped static singleton). All reads, writes, and transitions of the `PinRequestManager` state are serialized on the main thread. The button's enabled/disabled state mirrors `uiState == IDLE` (enabled only when IDLE). The press handler also re-checks the manager's state (in case a freshly recreated Activity temporarily shows an enabled button). The press branches as follows. If `uiState != IDLE`, do nothing. If `uiState == IDLE` but `workerRunning == true` or `unresolvedState != NONE`, do not start a new request; show the toast "A previous creation request is still unresolved. Please wait a moment and press again." (Japanese: `前の作成要求が未解決です。しばらく待ってからもう一度押してください`) and finish. Start a new request only when `uiState == IDLE && !workerRunning && unresolvedState == NONE`. First check with `isRequestPinShortcutSupported()`; if unsupported, show the toast "Could not create the shortcut" (Japanese: `ショートカットを作れませんでした`) and finish (do not send the request; the state stays `IDLE / false / NONE`).
2. First prepare the D7 token (reuse the stored one if present; otherwise generate a UUID and save it with `commit()` to the dedicated SharedPreferences file `a11y_off_token_prefs`. The real file is `a11y_off_token_prefs.xml`, and the `<exclude domain="sharedpref" path="..."/>` path in `fullBackupContent` and `dataExtractionRules` (`cloud-backup` / `device-transfer`) must match it exactly). If the save fails, show the toast "Could not create the shortcut" (Japanese: `ショートカットを作れませんでした`) and finish with the state unchanged at `uiState = IDLE`, `workerRunning = false`, `unresolvedState = NONE`. Do not send the creation request.
3. Call `ShortcutManager.requestPinShortcut()` on a **worker thread**, passing a `ShortcutInfo` (ID `a11y_off`, short label, long label, icon, an explicit intent to MainActivity with the D7 token extra and the D8 flags). The callback is null (no new component is created, so the approval/rejection result is not received. An `IntentSender` callback is notified on approval but not on rejection, so it cannot handle both). When the worker starts, the main thread increments `requestGeneration` by 1 and sets `uiState = REQUESTING`, `workerRunning = true`, `unresolvedState = NONE`, `pauseObserved = false`, `resumeObserved = false`, and starts the 30s `REQUESTING` timeout timer. The worker holds two local variables: `boolean resultEventPosted = false`, and a known-outcome variable (initial value `UNKNOWN`). The known-outcome variable is assigned when the API returns or the exception is caught, before the post is attempted, regardless of whether the post succeeds or fails; the post's success or failure must never change the recorded outcome. The worker calls `requestPinShortcut()` in `try / catch (Exception)`. When the API returns true/false, it records the known outcome (`KNOWN_TRUE` / `KNOWN_FALSE`) before attempting the post, then posts the normal result event to the main thread's `Handler`; on success it sets `resultEventPosted = true`. When an `Exception` occurs, the `catch (Exception)` block records the known outcome as `KNOWN_EXCEPTION` before attempting the post, then posts the normal exception event; on success it sets `resultEventPosted = true`. A fatal VM `Error` (such as `OutOfMemoryError`) is not caught; it is rethrown. The worker's finally block sends the **Error-specific recovery event** to the main thread's `Handler` **only when `resultEventPosted == false`** (a separate event from the normal result event, identified by generation number. It is not sent on normal completion or on a normal exception). The recovery event carries the known outcome. `PinRequestManager` processes the recovery event on the main thread and applies the carried outcome: `KNOWN_FALSE` applies the false path immediately (`workerRunning = false`, `uiState = IDLE`, `unresolvedState = NONE`, the failure toast "Could not create the shortcut" (Japanese: `ショートカットを作れませんでした`) is shown, no 60s restriction); `KNOWN_TRUE` applies the true path (`workerRunning = false`, `uiState = WAITING_CONFIRMATION`, `unresolvedState = CONFIRMATION_UNRESOLVED`, `pauseObserved = false`, `resumeObserved = false`, and the 30s `WAITING_CONFIRMATION` timer starts); `KNOWN_EXCEPTION` applies the false path; `UNKNOWN` (a true `Error`, no result) applies the Error-recovery path (`workerRunning = false`, `uiState` returns to `IDLE` if it is `REQUESTING`, and — because it is unknown whether the API accepted the request — `unresolvedState` moves to `CONFIRMATION_UNRESOLVED` and the 60s release timer starts; the button becomes enabled again, but for 60s a press shows the unresolved toast and blocks a new request). If the 30s `REQUESTING` timer is still running, cancel it (for the `KNOWN_TRUE` path, start the 30s `WAITING_CONFIRMATION` timer instead). A recovery event is processed only when its generation matches the current request generation, and the transition to `CONFIRMATION_UNRESOLVED` is performed only once (if the 60s release timer is already running, do not start another; this prevents double transitions from stale timers). The main thread applies the carried outcome; it must not downgrade a known outcome to `UNKNOWN`. The worker's finally must not change `workerRunning` directly (to preserve main-thread serialization). **Failure of event notification itself**: if a `Handler.post` returns false, that event does not reach the main thread. If the normal result event's post fails, `resultEventPosted` stays `false`, and the finally block sends a recovery event carrying the known outcome (see above). If the Error-specific recovery event's post fails, the worker's finally sets `workerRunning = false` directly (an exception to main-thread serialization. Post failure means the main thread is close to stopping, and state visibility takes priority). **Terminal state when the recovery event's own post fails**: (a) If the main thread is no longer alive (the usual cause of post failure), the process is terminating; no in-memory recovery is attempted or guaranteed, and a recreated process starts at `uiState = IDLE`, `workerRunning = false`, `unresolvedState = NONE` (the same as the process-death case). (b) If the main thread is alive, the already-scheduled 30s `REQUESTING` timeout still fires and converges the state to the Error-recovery terminal state (see step 8). If the timeout has already fired before the fallback runs, the re-armed guard (step 8) converges the state on its next firing. No in-memory state recovery is guaranteed when the process ends (a recreated process starts at `IDLE` / `NONE`). `workerRunning` is `volatile` or an `AtomicBoolean`. **Abnormal termination path**: if the `Executor` rejects the worker (`RejectedExecutionException` or similar) or an exception occurs immediately after startup, immediately restore `workerRunning = false`, `uiState = IDLE`, `unresolvedState = NONE`, cancel the timer, and show the toast "Could not create the shortcut" (Japanese: `ショートカットを作れませんでした`). **Handling of worker results**: no direct UI update is made to an old Activity instance, but `PinRequestManager` does not discard the worker's result (true / false / exception) even after the `REQUESTING` timeout; it transitions the unresolved-request state accordingly (step 8, path 2). The generation number is used only to invalidate old timer callbacks and to suppress direct UI updates to a discarded old Activity. The call is made while a foreground Activity exists, and that requirement is also satisfied via the worker thread.
4. Meaning of the return value: false means "the shortcut creation request could not be used" (besides an unsupported launcher, this includes restricted user profiles, App Lock, and similar); true means "the API returned true (the launcher supports this feature). Whether the shortcut was actually installed is undetermined". An exception means "the API call did not complete normally". **true does not guarantee successful installation** (even if the user rejects in the dialog, that cannot be known without a callback). When true, do not show a success toast (the system dialog and the home-screen display are the feedback).
5. When the worker returns `false` **within 30s**, or an exception occurs, cancel the `REQUESTING` timer, restore `workerRunning = false`, `uiState = IDLE`, `unresolvedState = NONE`, re-enable the button, and show the toast "Could not create the shortcut" (Japanese: `ショートカットを作れませんでした`).
6. When the worker returns `true` **within 30s**, cancel the `REQUESTING` timer, set `workerRunning = false`, `uiState = WAITING_CONFIRMATION`, `unresolvedState = CONFIRMATION_UNRESOLVED`, and reset `pauseObserved = false`, `resumeObserved = false`. Keep the button disabled and start the 30s `WAITING_CONFIRMATION` timer.
7. After entering the confirmation-waiting state (`uiState == WAITING_CONFIRMATION` or `unresolvedState == CONFIRMATION_UNRESOLVED`), record `pauseObserved = true` on the following `onPause`, and `resumeObserved = true` on the following `onResume`. Do not record `onPause` / `onResume` that occur during `REQUESTING` (before the API call completes). In the Android Activity lifecycle, `onPause → onResume` also occurs on switching to another app, on notifications, on screen lock, and similar, so it cannot prove that the pin confirmation dialog has ended; therefore `pauseObserved` / `resumeObserved` are recorded only as reference information for recovery and are **not** used as release conditions for `WAITING_CONFIRMATION` or unresolved requests. On `onResume`, the current Activity re-reads the `PinRequestManager` `uiState` and reflects the button's enabled/disabled state (`uiState == IDLE`).
8. UI recovery by timeout and release of unresolved requests take the following two paths. **(1) `WAITING_CONFIRMATION` timeout (30s) and release of the unresolved request (+60s)**: if `WAITING_CONFIRMATION` lasts 30s, restore the UI (`uiState` returns to `IDLE` and the button is re-enabled). However, keep `unresolvedState = CONFIRMATION_UNRESOLVED` and restrict new requests while it is unresolved (pressing the button shows the toast "A previous creation request is still unresolved. Please wait a moment and press again." (Japanese: `前の作成要求が未解決です。しばらく待ってからもう一度押してください`)). `CONFIRMATION_UNRESOLVED` is released to `NONE` only by the timeout **a further 60s after** the UI returns to `IDLE` (it is not released on `onPause → onResume`). **(2) `REQUESTING` timeout (30s) and state transitions on late worker completion**: when the 30s `REQUESTING` timeout fires, check `workerRunning` first. If `workerRunning == true`, apply the normal timeout transition: restore the UI (`uiState` returns to `IDLE` and the button is re-enabled), but keep `workerRunning == true` and set `unresolvedState` to `REQUESTING_UNRESOLVED` to restrict new requests. Also re-arm the timeout as a guard re-check 30s later: while the state remains `REQUESTING_UNRESOLVED` with `workerRunning == true`, the guard re-arms every 30s. On a firing where `workerRunning == false` and neither a result event nor a recovery event for the current generation has been processed, converge to the Error-recovery terminal state (`uiState = IDLE`, `unresolvedState = CONFIRMATION_UNRESOLVED`, 60s release timer) and stop re-arming. A result or recovery event cancels the guard (the late-completion path below applies). The guard is generation-checked; it applies only to the current request generation. If `workerRunning == false` and neither a result event nor a recovery event for the current generation has been processed — which on the main thread can only mean the emergency direct fallback ran, since every normal completion also moves `uiState` out of `REQUESTING` — do NOT transition to `REQUESTING_UNRESOLVED`; instead converge to the Error-recovery terminal state: `uiState = IDLE`, `unresolvedState = CONFIRMATION_UNRESOLVED`, and start the 60s release timer. (At this point the main thread does not know the API outcome, because neither event arrived; the conservative transition to `CONFIRMATION_UNRESOLVED` is accepted as a limitation. It applies only when the recovery event's own post has failed.) If the timeout has already fired before the fallback runs (the state is already `REQUESTING_UNRESOLVED`), the re-armed guard converges the state on its next firing; the timeout-first order is therefore no longer a terminal gap. After a normal timeout transition, when the worker finishes late (`workerRunning = false`): if the worker ends with **`false` or an exception**, the request did not reach the launcher, so **release `unresolvedState` to `NONE` immediately** and show the toast "Could not create the shortcut" (Japanese: `ショートカットを作れませんでした`). If the worker returns **`true`**, the request was accepted by the launcher late, so do not discard the result; **transition `unresolvedState` from `REQUESTING_UNRESOLVED` to `CONFIRMATION_UNRESOLVED`**, reset `pauseObserved = false`, `resumeObserved = false`, and release `unresolvedState` to `NONE` at the timeout **60s later**.
9. On Activity recreation (e.g. screen rotation): the new Activity inherits the manager's state. While a request is in progress, the state is not returned to IDLE; the button is enabled only when `uiState == IDLE` (disabled while `REQUESTING` / `WAITING_CONFIRMATION`). After the 30s timeout returns `uiState` to `IDLE`, the button becomes enabled again, but while `unresolvedState != NONE` or `workerRunning == true`, the press handler rejects a new request and shows the unresolved toast ("the button is disabled" and "the button is enabled but the request is rejected" are different states). A newly created Activity only re-reads the state at `onResume`; it must not treat (`uiState = REQUESTING`, `workerRunning = false`) as `IDLE`. The button stays disabled until the timeout path converges the state (see step 8). If a dialog is displayed, it belongs to the system; the app does not block it.
10. On process recreation: Activity recreation and process recreation are different failure cases. When the process ends, the in-memory `PinRequestManager` state is lost, and after process recreation it is initialized to `uiState = IDLE`, `workerRunning = false`, `unresolvedState = NONE`. Without persistence, v7 cannot identify (detect as an undetermined state) past unresolved requests after process recreation, and if a new request is made immediately after process recreation, a duplicate request may be sent to the launcher; this is a known limitation (under Android's specification, handling of multiple pending requests from the same package is left to the launcher implementation, and there is no guarantee that the launcher deduplicates them). Whether cross-process persistent request management is needed is decided from live verification results; in v7 it is stated only as an unsupported case.

### 3.2 Executing the shortcut

1. Tapping the home-screen shortcut launches MainActivity with an `ACTION_DISABLE_A11Y` intent (if it is already running, the intent arrives at `onNewIntent`).
2. MainActivity handles this action in both `onCreate` and `onNewIntent`. In `onNewIntent`, call `setIntent(intent)` to update the intent. MainActivity has no launchMode specified (standard), so without the flags (D8) a new instance would be created every time. With the flags, if an existing instance is present the intent arrives once at `onNewIntent`, and if none is present it is handled in `onCreate`. That the processing itself is idempotent (a second call after a disable shows "already off") is the breakwater against double execution.
3. The handler `handleDisableA11y()`:
   - First check the D7 token. When the intent extra does not match the stored value, ignore it silently (no toast, no disable).
   - Next check the `disableInProgress` flag. If a disable is already running, ignore it silently (this prevents duplicate execution and duplicate toasts). If none is running, set the flag, increment the operation generation number by 1, and assign it to this operation.
   - Take `BridgeAccessibilityService.getInstance()`.
   - When non-null: call `disableSelf()`. Do not show a success toast at this point. Notify success only after the service termination is confirmed (see the completion check below).
   - When null, check the Android-side state in three values (`MainActivity.getAccessibilityState()`, the existing `ENABLED_ACCESSIBILITY_SERVICES` read made three-valued. When `getString()` returns null, treat it as DISABLED; on exception, treat it as UNKNOWN):
     - DISABLED (confirmed that this service is absent from Settings): show the toast "Accessibility is already off" (Japanese: `補助機能はすでにオフです`) and finish.
     - ENABLED (confirmed that this service is present in Settings; the service is enabled but its instance is not connected — immediately after process recreation, while connecting, or while reconnecting): do not show "already off"; show the toast "Not connected to the service. Please check the status." (Japanese: `サービスに接続されていません。状態を確認してください`). Do not disable.
     - UNKNOWN (the Settings read itself failed): show the toast "Could not confirm the status." (Japanese: `状態を確認できませんでした`). Do not disable.
   - Completion check: after calling `disableSelf()`, when the `ACTION_A11Y_STATE_CHANGED` broadcast indicating service termination is received, re-check the Android-side state with `getAccessibilityState()`. If DISABLED, clear the flag and show the toast "Accessibility has been turned off" (Japanese: `補助機能をオフにしました`). If ENABLED, keep the flag (the broadcast may have been caused by another event). Ignore a broadcast that arrives while no operation is in progress (the flag is down).
   - The `disableInProgress` flag is static (shared within the process), so mutual exclusion also works across multiple Activity instances. Reads/writes of the flag and updates of the operation generation number are serialized on the main thread (broadcast receipt and timers are also processed on the main thread). On the 2s timeout, do not simply clear the flag; re-check the Android-side state. If DISABLED, clear the flag and show the toast "Accessibility has been turned off" (Japanese: `補助機能をオフにしました`). If ENABLED, keep the flag and re-check again after another 2s (up to 3 times. If it is still ENABLED after the re-checks, clear the flag and show the toast "Could not confirm the disable status." (Japanese: `無効化の状態を確認できませんでした`). The next call starts the determination from the beginning). If UNKNOWN, clear the flag and show the toast "Could not confirm the disable status." (Japanese: `無効化の状態を確認できませんでした`). If completion cannot be confirmed within 6s, do not assert success. Idempotency of the processing is maintained (a second call after a disable shows "already off").
4. After `disableSelf()`, the service sets `instance = null` in `onDestroy` and sends the existing `ACTION_A11Y_STATE_CHANGED` broadcast. MainActivity's state display is updated by the existing broadcast receipt / `onResume` (no new update path is created).
5. This processing is not a screen operation, so no in-operation notification ("in operation" / Override) is shown.

### 3.3 State and scope

- After the shortcut is executed, the server keeps running. `/health` returns ok, but screen operations such as `/state` return `ACCESSIBILITY_DISABLED` (503). The dashboard's 5-minute refresh also fails (because accessibility is disabled). This is the specified state, not a defect. It recovers when the user turns accessibility back on.
- `disableSelf()` disables the service without user confirmation (the API's specification). To prevent mistaken taps, the shortcut label uses wording that makes clear it turns the feature off. No additional confirmation dialog is shown at execution time (the shortcut itself is an explicit operation).
- On the possibility that another app sends an intent with the same action: MainActivity is `android:exported="true"` (a launcher Activity, confirmed in the manifest), so other apps can also send an explicit intent. However, without the D7 token it is ignored. The token can only be read by another app via ShortcutManager (another app can only obtain its own shortcuts), so a third party cannot realistically guess it. However, the token does not verify the calling app's identity; it is a Bearer Token scheme that accepts only intents carrying the secret. A replay by a third party that has obtained the token cannot be prevented. Treat the token as credentials and do not output it to logs. Remaining risks (such as a compromise of the launcher itself) are out of scope for this spec.
- On disable during an operation: even if `disableSelf()` is called in the middle of a screen operation, the server does not crash. The in-progress operation fails through the existing accessibility-disabled error path (the next request returns 503), and the in-operation notification becomes "operation ended" by the HttpBridgeServer-side automatic end timer, so it does not remain. The disable processing itself does not touch the server or the operation state.
- On managing creation requests: the request state is held by `PinRequestManager` (an Application-scoped static singleton) and separated from the Activity lifetime. It is separated into four independent states (`uiState`, `workerRunning`, `unresolvedState`, `pauseObserved` / `resumeObserved`), and all reads, writes, and transitions of the state are serialized on the main thread. When an Activity is recreated, the existing request state is carried over. While a request is running, a new request is not started. On late worker completion, no direct UI update is made to an old Activity, but `PinRequestManager` performs the state transition according to the result.
- On releasing unresolved requests: `onPause → onResume` also occurs on switching to another app and similar, so it cannot prove that the confirmation dialog has ended; record it only as reference information for recovery, and release `CONFIRMATION_UNRESOLVED` by the 60s timeout. `REQUESTING_UNRESOLVED` is released immediately when the worker ends with `false` / an exception, and moves to `CONFIRMATION_UNRESOLVED` and is released by the 60s timeout when it ends with `true`.
- On separating worker end and request end: manage the worker's running state separately with the `workerRunning` flag. Even after a REQUESTING timeout, do not allow a new request until the worker's end is confirmed. Ignoring results by generation number and the mutual exclusion of API calls are separate mechanisms. On Executor rejection or an exception immediately after startup, always bring `workerRunning` and the request state back into agreement. For an Error-specific recovery event, restore `workerRunning` to `false` and, if `uiState` is `REQUESTING`, return it to `IDLE`, and move `unresolvedState` to `CONFIRMATION_UNRESOLVED` and start the 60s release timer (do not set it to `NONE`, because the API acceptance status is unknown). A recovery event is identified by generation number and processed only when it matches the current request generation. The transition to `CONFIRMATION_UNRESOLVED` is performed only once; if the 60s release timer is already running, do not start another. The worker manages whether the normal result event has been posted with the local variable `resultEventPosted`, and the finally block sends the Error-specific recovery event only when `resultEventPosted == false` (it is not sent on normal completion or on a normal exception). The recovery event carries an outcome field (`KNOWN_TRUE` / `KNOWN_FALSE` / `KNOWN_EXCEPTION` / `UNKNOWN`); the main thread applies the carried outcome and must not downgrade a known outcome to `UNKNOWN`. If event notification itself fails, then when the normal result event's post fails, the finally block sends a recovery event carrying the known outcome, and when the Error-specific recovery event's post fails, the worker's finally sets `workerRunning` to `false` directly (an exception to main-thread serialization). If the recovery event's own post fails, the terminal state is as defined in §3.1 step 3: if the main thread is no longer alive, the process is terminating; if it is alive, the 30s `REQUESTING` timeout converges the state to the Error-recovery terminal state.
- On process recreation: PinRequestManager is in-process state management, and the state is lost when the process ends. After process recreation it is initialized to `IDLE` / `NONE`, but past unresolved requests cannot be identified, so there is a known limitation that a duplicate request may be sent. This is stated in v7 as an unsupported case. The terminal state when the recovery event's own post fails is defined in §3.1 step 3 (process termination, or convergence by the 30s `REQUESTING` timeout when the main thread is alive).
- On the timing of the success notification: do not notify success immediately after `disableSelf()`. Show "Accessibility has been turned off" (Japanese: `補助機能をオフにしました`) only after receiving the broadcast and confirming DISABLED. If it cannot be confirmed within 6s, do not assert success; show "Could not confirm the disable status." (Japanese: `無効化の状態を確認できませんでした`).
- On trusting the default launcher: in a shortcut creation request, the default launcher handles an intent containing the token. The default launcher is a principal inside the trust boundary. "Other ordinary apps cannot directly read SharedPreferences" and "the token is never exposed to any other software on the device" are not the same thing. Use of an untrusted launcher is out of scope. How the token is handled when backup / device transfer moves it to another device is confirmed separately. No token revocation / reissue mechanism exists in the current spec.
- On the three-valued state determination: `getAccessibilityState()` returns ENABLED / DISABLED / UNKNOWN. When `getString()` returns null, treat it as DISABLED (no enabled service exists); on exception, treat it as UNKNOWN. Keep the existing `isAccessibilityEnabled()` (boolean) for state display only; do not use it for the disable determination.

- AX-42: The token is not restored by an Android 12 or later cloud backup / restore.
- AX-43: The token is not restored by an Android 12 or later D2D device transfer (an independent test).
- AX-44: A disable by the old shortcut after a restore is rejected.
- AX-45: After a restore, a new token can be generated and the shortcut recreated.
- AX-46: During WAITING_CONFIRMATION and during `CONFIRMATION_UNRESOLVED`, an `onPause → onResume` does not release the request / unresolved request.
- AX-47: After a REQUESTING timeout, a new request is not started before the old worker ends.
- AX-48: Even if the old worker's end and a new Activity's state update interleave, the exclusion state is maintained.
- AX-50: The token is not restored by D2D transfer.
- AX-51: After `WAITING_CONFIRMATION` times out at 30s and `uiState` becomes `IDLE`, `CONFIRMATION_UNRESOLVED` is retained, a subsequent `onPause → onResume` is only recorded for reference, and it is released after 60s.
- AX-52: An `onPause → onResume` caused by switching to an unrelated app, a notification, or similar does not release the unresolved request.
- AX-53: After a `REQUESTING` timeout (30s), when the worker returns `true`, the result is not discarded; `unresolvedState` transitions from `REQUESTING_UNRESOLVED` to `CONFIRMATION_UNRESOLVED`, and the 60s confirmation-unresolved timer starts.
- AX-54: After a `REQUESTING` timeout (30s), when the worker ends with `false` or an exception, `workerRunning` becomes `false` and `REQUESTING_UNRESOLVED` is released to `NONE` immediately.
- AX-55: When the Executor rejects the worker's execution, the state recovers to `workerRunning = false`, `uiState = IDLE`, `unresolvedState = NONE`.
- AX-56: `workerRunning` and the `PinRequestManager` state changes are safely visible and consistent across threads through main-thread serialization (and appropriate synchronization).
- AX-57: The unsupported state after process recreation (IDLE initialization without persistence) and the launcher duplicate-request risk are stated in the spec.
- AX-58: The dedicated SharedPreferences real file name and the backup-exclusion XML (`fullBackupContent` and `dataExtractionRules` `cloud-backup` / `device-transfer`) `sharedpref` exclusion paths match.
- AX-59: Late true + Activity recreation (even if the worker returns true after a REQUESTING timeout and an Activity is recreated in between, `PinRequestManager` transitions to `CONFIRMATION_UNRESOLVED` and the new Activity's button state matches `uiState`).
- AX-60: Late false + Activity recreation (even if the worker ends with false / an exception after a REQUESTING timeout and an Activity is recreated in between, `REQUESTING_UNRESOLVED` is released immediately and the new Activity can recreate).
- AX-61: Race between the timeout and worker completion (even if the 30s timer fires and the worker completes at the same time, the state transition is processed atomically on the single main thread, and `uiState` / `workerRunning` / `unresolvedState` stay consistent).
- AX-62: Late execution of an old timer (even if an old timer callback from a changed generation runs late, it is invalidated and does not change the state).
- AX-63: The worker does not end for 90s or more (even if the worker does not end for a long time after a REQUESTING timeout, `unresolvedState` stays `REQUESTING_UNRESOLVED` and keeps restricting new requests, and transitions correctly when the worker ends).
- AX-64: When an exception occurs immediately after the worker starts, the state recovers to `workerRunning = false`, `uiState = IDLE`, `unresolvedState = NONE`.
- AX-65: Build-artifact inspection for backup exclusion (in the built APK / manifest, the `fullBackupContent` and `dataExtractionRules` `sharedpref` exclusion paths match the real file name `a11y_off_token_prefs.xml`).
- AX-66: Live verification of invalid intents (intents with no token, a mismatched token, null, or an empty string do not execute the disable and are ignored silently).
- AX-67: When a fatal VM Error occurs inside the worker, the finally block runs, the recovery event is notified to the main thread, and the Error is rethrown. However, if the normal result event has already been posted, the Error-specific recovery event is not sent (managed by the `resultEventPosted` flag).
- AX-68: The Error recovery event is processed on the main thread, `workerRunning` returns to `false`, and `uiState` returns to `IDLE` if it is `REQUESTING`, and `unresolvedState` moves to `CONFIRMATION_UNRESOLVED` and the 60s release timer starts. It is stated in the spec that no in-memory state recovery is guaranteed when the process ends.
- AX-69: When worker completion and the REQUESTING timeout race (both occur at the same time), no double state transition or double toast occurs.
- AX-70: Boundary-value test for all combinations of the token stored value and received value (stored null / empty string / UUID × received null / empty string / mismatch / match). When the stored or received value is null or an empty string, it is not treated as a match, and the disable is not executed.
- AX-71: After an Error, not only `workerRunning` but also `uiState` recovers (returns to `IDLE` if `REQUESTING`).
- AX-72: After an Error, the unresolved request is released by an appropriate timeout (it moves to `CONFIRMATION_UNRESOLVED` and becomes `NONE` after 60s).
- AX-73: Even if an Error occurs before or after the REQUESTING timeout, the final state is consistent (verify separately for before and after the 30s timeout. Particularly important. In both cases it finally converges to `CONFIRMATION_UNRESOLVED` and is released after 60s).
- AX-74: Even if the Error recovery event and an old timeout event race, no double transition occurs (identified by generation number; the transition is performed only once).
- AX-75: After Error recovery, once the unresolved period ends, a new shortcut creation request succeeds.
- AX-76: On normal true / false completion, the Error recovery event is not issued (`resultEventPosted == true`, so the finally block does not send it).
- AX-77: On Exception completion, the Error recovery event is not issued (only the normal exception event is sent).
- AX-78: The case where an Error occurs immediately after the API call completes but before the normal result notification (because the normal result event has not been posted, the finally block sends the Error-specific recovery event and the state moves to `CONFIRMATION_UNRESOLVED`).
- AX-79: The case where an old-generation Error recovery event arrives during a new request (identified by generation number and ignored).
- AX-80: Duplicate arrival of the Error recovery event (the transition is performed only once; no double transition occurs).
- AX-81: Failure to notify the main thread of a recovery event, covering both post-failure cases with outcomes. When the normal result event's post fails, the finally block sends a recovery event carrying the known outcome (`KNOWN_TRUE` applies the true path, `KNOWN_FALSE` / `KNOWN_EXCEPTION` apply the false path immediately with no 60s restriction), and the main thread applies the carried outcome without downgrading it to `UNKNOWN`. When the Error-specific recovery event's post fails, the worker's finally sets `workerRunning = false` directly, and the terminal state follows §3.1 step 3 (process termination, or convergence by the 30s `REQUESTING` timeout when the main thread is alive).
- AX-82 (P1): The Error recovery event's post fails; verify the complete resulting state. The worker's finally sets `workerRunning = false` directly. If the main thread is alive, the 30s `REQUESTING` timeout converges the state to the Error-recovery terminal state (`uiState = IDLE`, `unresolvedState = CONFIRMATION_UNRESOLVED`, 60s release timer). If the main thread is no longer alive, the process is terminating and a recreated process starts at `uiState = IDLE`, `workerRunning = false`, `unresolvedState = NONE`.
- AX-83 (P2): The normal false event's post fails; verify the fallback behavior and cooldown. With the outcome-carrying design, the recovery event carries `KNOWN_FALSE`, so the fallback applies the false path immediately (`workerRunning = false`, `uiState = IDLE`, `unresolvedState = NONE`, failure toast, no 60s restriction). The same outcome-carrying rule applies to a normal true event post failure, which must apply the true path (`WAITING_CONFIRMATION` + 30s timer) rather than the conservative fallback.
- AX-84 (P2): The exception event's post fails; verify the fallback behavior. The recovery event carries `KNOWN_EXCEPTION`, so the fallback applies the false path immediately (`workerRunning = false`, `uiState = IDLE`, `unresolvedState = NONE`, failure toast, no 60s restriction).
- AX-85 (P1, particularly important): The Error recovery post failure coincides with the `REQUESTING` timeout. Examine the interaction of the `REQUESTING` timeout, the `workerRunning` direct recovery, and the Error event delivery failure. When the 30s `REQUESTING` timeout fires with `workerRunning == false` and no result or recovery event processed, the state must converge to the Error-recovery terminal state (`uiState = IDLE`, `unresolvedState = CONFIRMATION_UNRESOLVED`, 60s release timer) instead of `REQUESTING_UNRESOLVED`. Objective: the system cannot enter a permanently inconsistent state. (This is the terminal-state convergence rule.)
- AX-86 (P2): A recovery event is successfully enqueued but processing is delayed. Verify that successfully enqueued events remain correctly associated with their request generation even when main-thread processing is delayed — for example, a recovery event posted before a new request starts must not be applied to the new request. This distinguishes event submission from event consumption.
- AX-87 (P2): Activity recreation after emergency worker-flag recovery. After the emergency direct recovery (the worker sets `workerRunning = false` directly), a recreated Activity must read the state correctly: it must not treat (`uiState = REQUESTING`, `workerRunning = false`) as `IDLE`; the button stays disabled until the timeout path converges the state.
- AX-88 (P2): An Error recovery event from an old generation arrives after timeout. The generation check ignores it; no double transition occurs.
- AX-89 (P1, mandatory regression test): The `REQUESTING` timeout fires before the emergency fallback (`workerRunning == true` at timeout time, so the state moves to `REQUESTING_UNRESOLVED` and the guard is re-armed); the fallback then runs (the worker sets `workerRunning = false` directly). The re-armed guard converges the state to `CONFIRMATION_UNRESOLVED` (`uiState = IDLE`, 60s release timer) on its next firing. No permanent `REQUESTING_UNRESOLVED` remains.
- AX-90 (P2): The known-outcome variable is assigned before the normal event's post is attempted, regardless of post success/failure. Verify that a post failure does not reset the outcome to `UNKNOWN` (the recovery event carries the known outcome).
- AX-91 (P2): The normal true event's post fails; the recovery event carries `KNOWN_TRUE` and the main thread applies the true path (`uiState = WAITING_CONFIRMATION`, `unresolvedState = CONFIRMATION_UNRESOLVED`, 30s timer).
- AX-92 (P2): The recovery event's post fails while the main thread is alive; the fallback sets `workerRunning = false` directly, and the timeout (or the re-armed guard) converges the state to `CONFIRMATION_UNRESOLVED`.
- AX-93 (P2): The 60s release timer is started only once; the guard's convergence does not start a second 60s timer when one is already running (no double transition).
- AX-94 (P2): Worker end and timeout concurrency: the worker completes at the same time as the `REQUESTING` timeout fires; the final state is consistent (exactly one transition, no double release).
- AX-95 (P2): A recovery event processed after the timeout is generation-checked; a stale-generation event is ignored and does not re-transition the state.

### Responsibility split

- Python tests prove only the source structure (the shortcut definition, the action handling, the null branches, the `disableSelf()` call, the absence of a server stop, and manifest immutability).
- Java runtime behavior (the pin dialog display, launching from the shortcut, the actual disable, and toast display) cannot be proved by Python tests. Cover it with code review (visual confirmation at implementation time) and live-device verification (§5). The absence of a Java unit-test environment is not a reason to reject this spec.

## 5. Live verification (live device, v2.9.3)

- AX-L1: In-app button → system pin confirmation dialog → confirm → the shortcut appears on the home screen. If the dialog is cancelled, no shortcut is created and there is no crash. After the 30s timeout the button becomes enabled again, and during the further 60s unresolved-request restriction period a press shows the unresolved toast; after it passes, recreation becomes possible.
- AX-L2: Tap the shortcut → accessibility turns off (the Settings toggle is off, `/health` accessibility is false).
- AX-L3: Tap the shortcut again while off → the toast "Accessibility is already off" (Japanese: `補助機能はすでにオフです`) is shown and there is no crash. When the service is enabled but the instance is null, "Not connected to the service. Please check the status." (Japanese: `サービスに接続されていません。状態を確認してください`) is shown (if this is hard to reproduce, confirm it by code review).
- AX-L4: After the shortcut is executed, the server keeps running (`/health` is ok) but `/state` returns 503 (scope check).
- AX-L5: Turn accessibility back on in Settings → screen operations work again (`/health` accessibility is true).
- AX-L6: Disable during an operation — start a screen operation from Bridge and execute the shortcut during it. The operation ends or fails appropriately, the server keeps running, the in-operation notification does not remain, and the next request returns 503.
- AX-L7: Repeated execution — tap the shortcut repeatedly. Even if multiple Activities are created, there is no abnormal processing, the server does not stop, and it finally becomes disabled. Toasts are not shown in large numbers.

## 6. Edge cases

- When the launcher does not support pinning at shortcut creation time: `requestPinShortcut()` returns false, a toast is shown, and it ends. No crash.
- When the shortcut is tapped while the service is not connected: if `getInstance()` is null, check the Android-side state. If DISABLED, show "Accessibility is already off" (Japanese: `補助機能はすでにオフです`); if ENABLED, show "Not connected to the service. Please check the status." (Japanese: `サービスに接続されていません。状態を確認してください`); if UNKNOWN, show "Could not confirm the status." (Japanese: `状態を確認できませんでした`). None of them disables (the same determination as §3.2).
- When the server stops during shortcut execution: server stop and accessibility disable are separate states. Even if the server stops, the accessibility enabled state does not change, so do not show "already off". Check the Android-side state and show a toast according to the result. No crash.
- When reading the state confirmation fails (UNKNOWN): show "Could not confirm the status." (Japanese: `状態を確認できませんでした`) and do not disable.
- When the device is restarted: the home-screen shortcut remains (launcher specification). The accessibility on/off state follows the pre-restart state (Android specification).
- When the shortcut is removed from the home screen: the app-side state does not change. To recreate it, press the button inside the app again.
- When an intent with no token extra arrives: ignore it silently (no toast, no disable).
- Repeated taps on the create button: while a request is in progress the button is disabled, so no double request is sent.
- When a creation request is in progress during Activity recreation: the new Activity inherits the `PinRequestManager` state. The button is enabled only when `uiState == IDLE` (disabled while `REQUESTING` / `WAITING_CONFIRMATION`). After the 30s timeout returns `uiState` to `IDLE`, the button becomes enabled again, but while `unresolvedState != NONE` or `workerRunning == true`, the press handler rejects a new request. Late worker results are not discarded; `PinRequestManager` performs the state transition according to the result (the generation number is used only to invalidate old timer callbacks and to suppress direct UI updates to a discarded old Activity). A newly created Activity only re-reads the state at `onResume`; it must not treat (`uiState = REQUESTING`, `workerRunning = false`) as `IDLE`. The button stays disabled until the timeout path converges the state.
- When a late broadcast arrives: if no operation is in progress, ignore it. If an operation is in progress, re-check the Android-side state and clear the flag only when DISABLED. When ENABLED, keep it.
- After the 30s timeout restores the UI while the confirmation dialog is still shown: it is recorded as an unresolved request and new requests are restricted (a toast is shown). `onPause → onResume` is recorded only as reference information, and the unresolved request is released by the timeout a further 60s later.
- After restoring from a backup: the token is excluded from restore, so it does not exist and the old shortcut does not work. Recreate it from the button inside the app (a new token is generated).
- When `onPause → onResume` arrives during confirmation waiting or while an unresolved request is held: because it cannot be distinguished from switching to another app and similar, record it only as reference information for recovery and do not release the unresolved request. Release is done only by the timeout path.
- When the worker is still running after the `REQUESTING` timeout: restrict new requests as an unresolved request (`REQUESTING_UNRESOLVED`). Afterwards, when the worker ends with `false` or an exception, release the unresolved request immediately; when it returns `true`, move to `CONFIRMATION_UNRESOLVED` and restrict new requests for a further 60s. Note: when the worker delay is long, the total of the REQUESTING timeout (30s) + worker delay + 60s can exceed 90s (the normal path's maximum of 90s is the upper bound when the worker completes within 30s).
- When a fatal VM Error occurs in the worker: no result event returns. The worker's finally sends the Error-specific recovery event to the main thread (only if no normal result event has been posted), carrying the known outcome. `PinRequestManager` applies the carried outcome on the main thread: `KNOWN_FALSE` / `KNOWN_EXCEPTION` apply the false path immediately (`workerRunning = false`, `uiState = IDLE`, `unresolvedState = NONE`, failure toast, no 60s restriction); `KNOWN_TRUE` applies the true path (`uiState = WAITING_CONFIRMATION`, `unresolvedState = CONFIRMATION_UNRESOLVED`, 30s timer); `UNKNOWN` applies the Error-recovery path (`workerRunning = false`, `uiState` returns to `IDLE` if it is `REQUESTING`, `unresolvedState` moves to `CONFIRMATION_UNRESOLVED` and the 60s release timer starts). If the REQUESTING timeout (30s) has already fired, the state converges to the same unresolved state. Double transitions from stale timers are prevented by generation number. No in-memory state recovery is guaranteed when the process ends.
- When the Error recovery event's own post fails: the worker's finally sets `workerRunning = false` directly. If the main thread is no longer alive (the usual cause of post failure), the process is terminating; no in-memory recovery is attempted or guaranteed, and a recreated process starts at `uiState = IDLE`, `workerRunning = false`, `unresolvedState = NONE`. If the main thread is alive, the already-scheduled 30s `REQUESTING` timeout still fires and converges the state to the Error-recovery terminal state (see §3.1 step 8). If the timeout has already fired before the fallback runs (the state is already `REQUESTING_UNRESOLVED`), the re-armed guard (§3.1 step 8) converges the state to the Error-recovery terminal state on its next firing. The timeout-first order is therefore no longer a terminal gap.
- After the process ends: the `PinRequestManager` state is lost. After the app restarts it is initialized to IDLE, but whether the previous request succeeded is undetermined. A duplicate request may be sent (under Android's official specification, handling of multiple pending requests from the same package is left to the launcher, and behavior such as ignoring the previous request depends on the launcher and is not guaranteed). In v7 this is stated as an unsupported case.
- After a D2D device transfer: the dataExtractionRules device-transfer exclusion means the token is not restored to the new device. The old shortcut does not work. Recreate it from the button inside the app.

## 7. Out of scope (not doing)

- Automatic turn-off linked to Bridge off (set aside in D1). If a future version lets Settings choose on/off, that is a separate spec.
- A shortcut to turn accessibility back on (impossible under Android restrictions).
- Turning it off from the quick settings tile (the tile is for the existing start/stop. Kept as a future extension candidate).
- A confirmation dialog at execution time (the shortcut itself is an explicit operation, so none is shown).
- Execution without a screen transition via a transparent Activity (in v1, MainActivity opening briefly is acceptable).
